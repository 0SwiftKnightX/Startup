Each AI should have a unique identity and should be addressed by name when
multiple AI instances are active.
AI-to-AI references should explicitly identify the intended participant.
The team should avoid assuming that an AI heard another conversation unless that
information has been explicitly communicated or recorded.
Important meetings, handoffs, decisions, and unresolved questions should be
persisted in repository documents so chat history is not the only source of truth.

RECOMMENDED DEVELOPMENT LOOP
1. Define the objective and acceptance criteria.
2. Inspect the existing repository and relevant systems before changing anything.
3. Identify dependencies and integration points.
4. Implement the complete feature path needed for the objective.
5. Run automated verification.
6. Produce evidence of what was tested and what passed or failed.
7. Test the actual integrated game behavior where applicable.
8. Perform Product Owner acceptance testing on the target hardware when hardware
   behavior is involved.
9. Record the result.
10. Only then treat the work as complete.

DEFINITION OF DONE
A feature is not considered complete merely because:
- code was written;
- a script parses;
- a build succeeds;
- a unit test passes; or
- an AI reports that the task is finished.

Completion should mean that the intended functionality is integrated into the
project, can be exercised through the intended user path, has appropriate
automated verification, and has target-device acceptance when required.

EVIDENCE-FIRST VERIFICATION
The repository should eventually contain a reusable verification foundation.
The verifier should be capable of checking project integrity beyond superficial
syntax, including relevant tests, project loading, and clearly reported pass/fail
results.

GitHub Actions should automate repeatable checks where practical.
Automated verification does not replace real Quest 3S acceptance testing.
A successful CI run proves what CI tested; it does not automatically prove that
the complete player experience works on the headset.

QUEST 3S QUALITY PRINCIPLE
Meta Quest 3S is the first target device established by the current README.
Quest hardware should therefore remain part of the verification loop.
PCVR/editor preview can accelerate development, but hardware validation remains
necessary for tracking, interaction, performance, comfort, Android behavior, and
other device-specific issues.

REPOSITORY GOVERNANCE RECOMMENDATION
The repository should preserve a clear distinction between:
- current project direction;
- approved decisions;
- recommendations;
- active work;
- completed work;
- verification evidence;
- Product Owner acceptance;
- meetings and handoffs;
- unresolved questions.

Persistent records should be named predictably and should not proliferate into

ANTI-REWORK PRINCIPLES
Before implementing a system, determine:
- what owns the data;
- where the data lives;
- what consumes it;
- what other systems depend on it;
- how it is tested;
- how it is exposed to the player;
- how it is persisted;
- how failure is handled;
- how the feature will be verified on its target platform.

Avoid creating parallel systems that solve the same problem without an explicit
reason. Avoid cross-system shortcuts that make ownership unclear. Prefer simple,
well-defined interfaces and predictable data flow.

ANTI-AI-SLOP PRINCIPLES
AI-generated work should be judged by integration, correctness, maintainability,
evidence, and actual behavior rather than by volume of generated code.
No AI should claim completion without evidence.
No AI should hide uncertainty.
No AI should create unnecessary architecture merely to appear sophisticated.
No AI should modify unrelated systems to complete a narrowly scoped task without
identifying the dependency and its reason.

QUALITY TARGET
The project should be developed toward professional game-production standards:
coherent architecture, reliable systems, performance awareness, accessibility
and comfort where applicable, maintainable code, repeatable verification,
documented decisions, and real-device validation.
