# Project Startup Handoff Template — Version 1.1

Version 1.1 is an additive refinement of Version 1.0. Version 1.0 remains preserved.

## 1. Handoff Metadata

Every handoff records:

- Date: YYYY-MM-DD
- Time: HH:MM:SS UTC
- Eastern Time: HH:MM:SS with America/New_York and EDT (UTC-04:00) or EST (UTC-05:00)
- Title
- Signed by: AI working name
- Project function
- Handoff Template Version

Filename:
Project Startup Handoff - YYYY-MM-DD - HHMM - Short Title.md

Never overwrite historical handoffs.

## 2. AI Working Identity and Naming

Every AI entering Startup assigns itself a working name before substantive work.

Rules:

1. Choose your own working name.
2. Never claim or inherit the identity of the AI whose handoff you read.
3. Never imply you are the previous AI merely because you received its handoff.
4. The name identifies the current AI/session identity, not ownership of previous work.
5. Declare a project function.
6. Sign worklogs, audits, and handoffs with that name/function.
7. Check recent handoffs/worklogs for name collisions.
8. If you choose a name already used, append a collision suffix such as #2 or #3.
9. A collision suffix identifies a distinct AI/session and is not the previous agent.

## 4. Entry Rule

1. Read Project Bible.
2. Read active Handoff Template.
3. Read applicable recent handoff records.
4. Inspect current repository.
5. Audit AI/tool/plugin environment separately.
6. Assign working name and function.
7. Produce a read-only entry audit.
8. Present work avenues.
9. Obtain user authorization.
10. Then modify the repository.

## 5. Project Boundary

Startup is the game/XR project. The Standalone AI is separate. Do not merge its architecture, memory, or identity into Startup without explicit authorization.

## 6. Entry Audit

Record repository branch/HEAD, recent activity, implemented/partial/missing/unknown/broken/planned systems, code/integration findings, verifier/CI/build state, runtime state, Quest evidence, recent work, and important discoveries.

## 7. AI Environment Audit

Keep project state and AI-environment state separate.

Audit:
Features → Tools → Plugins/Apps → Definitions → Functions → Function Definitions → Skills → Skill Definitions → Connection → Authorization → Actual Verification.

Do not equate tool exposure or plugin existence with successful execution.

## 8. Work Avenues

Typical avenues include XR foundation, gameplay, vehicles, world/environment, NPCs/creatures, inventory/items/economy, AI/spatial systems, persistence, verification/CI, performance/Quest, infrastructure, research, and custom scope.

## 9. Authorization Handshake

State scope, current findings, dependencies, blockers, files/systems, exclusions, authorization, modifications, verification, completed work, and remaining work.

## 10. Operating Sequence

HANDOFF → AUDIT → UNDERSTAND → VERIFY → CONTINUE

PRESERVE → INSPECT → UNDERSTAND → PLAN → MODIFY → VERIFY

## 11. Evidence Rule

Never equate code existence with working functionality.

Use:
DESIGN, IMPLEMENTED, STATIC VERIFIED, CI VERIFIED, RUNTIME VERIFIED, QUEST VERIFIED, PRODUCTION VERIFIED.

Use precise labels:
IMPLEMENTED, PARTIAL, PLANNED, UNKNOWN, FAILED, BLOCKED, UNVERIFIED.

## 12. Worklog and Changelog Continuity

Every substantive change is attributable.

- Append completed work to the active GPT worklog.
- Update CHANGELOG.md for structural, configuration, dependency, or user-facing changes.
- Record validation and limitations.
- Corrections are appended rather than silently rewriting history.
- A completed handoff identifies the worklog/changelog records produced during the session.

## 13. Reference and Code-Reuse Provenance

Reference repositories are research sources, not automatic permission to copy.

Before copying code/assets/documentation:

1. Identify the exact source repository and path.
2. Inspect its license and path-specific notices.
3. Confirm the intended reuse is permitted.
4. Preserve required notices.
5. Record source, license, and reused scope in provenance/worklog documentation.
6. If licensing or permission is unclear, do not copy it; use it as conceptual reference or obtain permission.

Prompts should prefer proven compatible implementations when legally reusable, but never bypass licensing or attribution.

## 14. Change Governance

Unless explicitly authorized, do not delete/rename/restructure files, replace architecture, change major dependencies or Godot/XR/Android/CI architecture, weaken verification, bypass failed validation, or claim Quest functionality without physical evidence.

## 15. Handoff Record

Each record in `Project Bible/Handoffs/` must contain date, UTC time, Eastern Time with EDT/EST and offset, title, signing AI name, project function, template version, repository identity, purpose, transferred state, findings, completed work, worklog/changelog records, verification, remaining work, ownership/authorization notes, provenance where applicable, and next continuation state.

## 16. Template Versioning

- Version 1.0 — initial protocol
- Version 1.1 — identity, Eastern Time, continuity, and provenance refinement
- Version 1.2 — future refinement
- Version 2.0 — major protocol change

Preserve older templates and never rewrite historical handoffs to pretend they used a newer version.

## 17. Project Bible Relationship

Project Bible = durable intent and rules.

Handoff Template = context-transfer protocol.

Handoff Records = historical transfers.

Worklogs, changelogs, audits, and validation records = ongoing activity/evidence.

## 18. Completion Rule

A handoff is complete only when project/excluded project, authoritative repository, current state, recent activity, unresolved work, verified/unknown state, requested scope, authorized scope, exclusions, next action, signing identity, and exact timestamp are identified.
